# Q. 패러다임 진화사 — 절차·객체·함수형·관점지향 (외부 경계, 상기용)

## 무엇이 궁금한가
- 프로그래밍 패러다임의 큰 흐름: 절차적 → 객체지향 → 함수형 → 관점지향. 각자 왜 생겼고 무엇을 해결했으며, 정말 직선 진화인가.
- [[지침]]의 외부 학습 경계(OOP·디자인 패턴)상 이 프로젝트에서 깊게 파지 않는다. 다만 역사·흐름 자체는 언어 설계 의도를 읽는 배경이라, 잊지 않도록 **상기용 요약**으로 남긴다.

## 토론에서 짚은 줄거리 (2026-06-18, 상기용)
- **절차적** — 소프트웨어 위기(1960s) → 다익스트라 "Goto Considered Harmful"(1968) → 구조적 프로그래밍 → 절차적 정립(C). 프로그램 = 데이터에 작용하는 함수(프로시저)들의 모음. ([[C 제어문 — 점프로 본 분기·반복]])
- **절차적의 한계** — 데이터와 함수가 따로 논다. 규모가 커지면 전역 상태 통제 불가, 현실 사물 모델링이 어색.
- **Simula(노르웨이, 1960s)** — 시뮬레이션 도구로 만들다 "상태+행동을 묶은 클래스/객체/상속"을 발명. OOP *언어 장치*의 출처. C++이 여기서 클래스를 베낌.
- **Smalltalk/PARC(앨런 케이, 1970s)** — "object-oriented"라는 말과 "모든 것은 객체, 계산은 메시지 전달"이라는 순수 비전. 이름·비전 = PARC, 장치 = Simula.
- **대중화** — C++(속도+객체) → Java(1995, 안전·쉬운 OOP)로 업계 기본값이 됨. 학부가 C++을 "OOP의 핵심"으로 가르친 잔향.
- **함수형 — 사실 더 오래됨** — 람다 대수(1930s), Lisp(1958, C보다 위). 오래 비주류였다가 멀티코어(불변 = 동시성 안전)·빅데이터로 2000~2010s 부활. Java 8·C++11 람다로 흡수. "교체"가 아니라 "오래된 혈통의 귀환".
- **관점지향(AOP)** — PARC의 키잘레스, 1990s 말, AspectJ. cross-cutting concern(로깅·보안·트랜잭션)이 여러 모듈에 흩뿌려지는 걸 따로 떼어 끼움. 주류는 못 됨, 프레임워크(스프링) 도구로 생존. 교체자가 아닌 **보완자**.
- **큰 그림** — 직선 진화가 아니다. 절차→OOP는 진짜 관점 전환, 함수형은 평행 혈통의 부활, AOP는 보완. 오늘의 현실은 **멀티패러다임**이고 그 대표가 C++(절차·OOP·제네릭·함수형을 다 얹음) → [[C++이란 무엇인가 — OOP 편한 C를 넘어서]]의 "무게중심은 OOP 하나가 아니다"와 만난다.
