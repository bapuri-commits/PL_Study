# C 순회와 난수 — for-each·이터레이터와 랜덤

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 문법_ C ver]]의 토론에서 파생되었습니다. (2026-06-17)

## 핵심 요약
> 둘 다 같은 대비를 보여준다: **C는 원시적·전역, C++/Java는 추상화·객체화.** for-each는 C엔 없는 문법으로, 그 엔진은 **이터레이터**(C 포인터 `* ++ !=`의 일반화)다. "어떻게 순회하나"를 자료구조에 위임해 인덱스 실수를 없애고 자료구조별 효율 순회를 같은 문법으로 가능케 한다. 난수는 **의사난수**(seed가 같으면 수열도 동일한 결정적 계산)이며, C는 `rand`/`srand` 전역 하나에 엔진·분포가 뭉쳐 있고, C++/Java는 이를 객체로 분리한다.

## 내용

### for-each — 이터레이터의 표면
- **C엔 for-each가 없다.** C는 전통적 인덱스 for(`for(int i=0; i<n; i++)`)뿐이다. `for (e : v)` 형태는 C++(`for (auto e : v)`, C++11)·Java(`for (E e : list)`)에서 나중에 들어왔고, 계열로 보면 Python `for...in`, C# `foreach`, JS `for...of`도 같은 부류다.
- **도입 동기 둘**
    1. **의도 표현 + 실수 제거** — 정작 원하는 건 원소(`arr[i]`)인데 인덱스 for는 수단인 `i`를 노출한다. 그 `i`가 곧 실수 지점(`<=` off-by-one, 시작값, 루프 안에서 `i` 훼손 등). for-each는 `i`를 숨겨 이 실수를 구조적으로 불가능하게 만든다.
    2. **자료구조별 효율 순회** — 연결 리스트를 인덱스 접근(`list[i]`)으로 돌면 매번 처음부터 따라가 **O(n²)**로 터진다. 자료구조마다 "효율적 접근법"이 다른데 인덱스 for는 배열식 `[i]`를 강제한다.
- **엔진 = 이터레이터.** "다음 원소로 가는 법"을 자료구조 본인에게 위임한다. 배열은 "주소 +1", 리스트는 "next 포인터 따라가기" 등. `for (auto e : v)`는 대략 이렇게 풀린다.
```cpp
for (auto it = v.begin(); it != v.end(); ++it) {
    auto e = *it;        // 현재 원소 (인덱스 for의 arr[i])
    처리(e);
}                        // ++it = "다음으로"(자료구조가 정의), it != end() = 끝 검사
```
- **복잡도 주의(오개념 방지)** — 이터레이터가 복잡도를 마법처럼 낮추는 게 아니다. **잘못된 접근(리스트에 `[i]`)을 강제하지 않아 O(n²) 함정을 애초에 안 만드는** 것이다. 리스트를 이터레이터(next 따라가기)로 돌면 각 스텝 O(1) → 전체 O(n). 배열을 인덱스 for로 도는 건 원래도 O(n)이라 개선이랄 게 없다.
- **C++ 이터레이터 = C 포인터의 일반화.** C에서 이미 포인터가 원시적 이터레이터였다(`for (int *p=arr; p<arr+n; p++) 처리(*p);` — `*`·`++`·`!=`로 순회). C++은 이 인터페이스를 다른 컨테이너도 흉내 내게 해서, 배열이든 `vector`·`list`든 **쓰는 쪽이 구분 없이** `*it`/`++it`로 순회하게 했다. 이게 STL 알고리즘(`sort`, `find`가 begin·end만 받음)이 모든 컨테이너에 도는 토대다 → [[제네릭·템플릿 비교]].
- 추상화 원리의 사례 — 내부(순회 방법)는 숨기고 표면(`for e : v`)만 노출([[언어란 무엇인가 — 분류와 컴파일·실행 모델]]).

### 난수 — 의사난수와 객체화
- **의사난수(pseudo-random).** `rand()`는 결정적 함수다. 내부 상태에 `다음 = f(현재)`를 적용해 수열을 만든다(선형 합동법 등). **시작점(seed)만 정해지면 그 뒤 수열은 완전히 고정**이다.
    - `srand`를 아예 안 부르면 seed가 `1`로 가정되어, **매 실행마다 똑같은 수열**이 나온다.
    - `srand(time(NULL))`은 실행 시각(초)으로 seed를 매번 바꿔 수열을 달라지게 한다.
    - 재현성은 단점만이 아니다 — "같은 seed = 같은 결과"는 리플레이·디버깅·테스트에서 **기능**이 된다(버그 재현). 무작위성↔재현성은 trade-off이고 seed가 그 스위치.
- **C의 약점** — `rand() % N`은 분포가 미세하게 치우친다(범위가 N의 배수가 아니라 작은 수가 살짝 잦음). `time(NULL)`은 초 단위라 1초 내 두 실행은 같은 seed. 엔진 상태가 전역 하나라 독립적인 난수열을 여러 개 못 굴린다.
- **객체화 — C++/Java는 뭉친 것을 쪼갰다.** C는 (1)엔진과 (2)분포가 `rand()%6` 한 줄에 뭉쳐 있다. 분리하면:

| | 엔진/생성기 | 분포·범위 | 인스턴스 |
|---|---|---|---|
| C | `rand()` 전역 하나(고정) | `% N` 수동(치우침) | 전역 1개 |
| C++ | 엔진 **객체**, 종류 선택 | **분포 객체**로 분리 | 여러 개 |
| Java | `Random` **객체** | 메서드 인자(`nextInt(6)`) | 여러 개 |

- C++의 "엔진 ⊗ 분포 분리"는 조합 가능한 부품 설계(이터레이터의 그 철학과 같은 결). 분포 객체만 바꾸면 균등·정규 등으로 갈아끼운다.

## 코드
```c
// C — 전역 rand/srand
srand(time(NULL));
int r = rand() % 6;          // 0~5 (분포 미세 치우침)

// C — 포인터로 순회 (원시적 이터레이터)
for (int *p = arr; p < arr + n; p++)
    처리(*p);
```
```cpp
// C++ — range-based for + 난수(엔진/분포 분리)
for (auto e : v) 처리(e);

std::mt19937 engine(seed);
std::uniform_int_distribution<> dice(1, 6);
int r = dice(engine);        // 1~6 균등, % 치우침 없음
```
```java
// Java — enhanced for + Random 객체
for (int e : arr) 처리(e);

Random rng = new Random();
int r = rng.nextInt(6);      // 0~5
```

## 다른 언어에선?
- 본문 자체가 비교라 핵심 대비만 재확인 — **C는 전역 함수 하나에 다 뭉쳐 간단하지만 거칠고(순회는 인덱스 강제, 난수는 품질·분포·독립성 약함), C++/Java는 객체/인터페이스로 쪼개 제어력과 안전성을 준다.** [[C 자료형 — 정수와 실수의 표현]]부터 반복된 "자유·하드웨어 밀착 vs 안전·명시"의 또 다른 사례.
- 이터레이터 표현 차이 — C++은 포인터를 본뜬 연산자(`* ++`), Java는 `Iterator` 인터페이스 메서드(`hasNext()`/`next()`).

## 막힌 것 / 의문
- **이터레이터는 디자인 패턴의 한 줄기** — [[지침]]의 외부 학습 경계상 패턴 자체는 깊게 안 판다. "for-each의 엔진이 이터레이터"까지가 문법 맥락이고, 패턴으로서의 깊이는 디자인 패턴 정리와 "거긴 어떻게 했어?"로 연결.
- **난수 품질·보안** — 메르센 트위스터(`mt19937`) 알고리즘, 암호학적 난수(`SecureRandom`, `/dev/urandom`)는 알고리즘·보안 영역이라 경계 밖. "C++/Java는 더 나은 엔진을 고를 수 있다"까지만.
- **본격 비교는 후속** — 이터레이터→템플릿/STL은 [[제네릭·템플릿 비교]], 난수 객체화는 C++/Java 폴더가 생기면 확장. 지금은 C 기준점 + 비교 씨앗만.
