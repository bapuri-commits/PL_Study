# C 제어문 — 점프로 본 분기·반복

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 문법_ C ver]]의 토론에서 파생되었습니다. (2026-06-17)

## 핵심 요약
> 모든 제어 구조는 기계 수준에서 **두 가지 점프의 조합**으로 환원된다: 조건부 점프(플래그를 보고 갈지 결정) + 무조건 점프. 순차 실행은 PC(다음 명령 주소 레지스터)의 자동 +1이고, 분기·반복은 그 PC를 강제로 바꾸는 일이다. `if`는 조건을 뒤집은 조건부 점프, `while`은 거기에 위로 되돌아가는 무조건 점프를 더한 것, `switch`는 값으로 진입점만 계산해 점프(탈출은 `break`가 담당), `goto`는 점프를 그대로 노출한 것이다.

## 내용

### 토대 — PC와 점프
- CPU는 **PC(Program Counter, =IP)** 라는 레지스터에 "다음에 실행할 명령의 주소"를 들고 있다. (기계어는 이름이 아니라 주소로 식별 — [[언어란 무엇인가 — 분류와 컴파일·실행 모델]].)
- **순차 실행의 정체** = fetch → execute → **PC 자동 +1** → 반복. "비트 순서대로 읽는다"는 게 기계 수준에선 이 PC 자동 증가다.
- **점프(jump)** = PC에 +1이 아니라 지정한 주소를 강제로 넣어 흐름을 끊는 명령. 두 종류.
    - **무조건 점프** — 그냥 "저기로 가".
    - **조건부 점프** — CPU가 비교(`a > b` 등)를 하면 결과를 **플래그 레지스터**에 흔적으로 남기고, 조건부 점프는 그 플래그를 보고 "점프할지 / 그냥 +1로 흘릴지" 정한다.
- **결론 — 제어 구조는 이 둘의 조합이면 충분하다.** (원본글 "어떻게 제어되는 구조를 설계하나"의 답.)

### if — 조건을 뒤집은 조건부 점프
- `if (a > b) { X }`는 기계 수준에서 조건을 **부정해서** 짠다.
```
    a, b 비교            ; 플래그 기록
    조건부 점프(거짓이면) → L1   ; 'a>b 거짓'이면 X 건너뜀
    X 실행               ; (참이면 점프 안 하고 그냥 흘러옴)
L1: ...
```
- 왜 "참이면 점프"가 아니라 "거짓이면 건너뛰기"인가 — 두 이유가 같은 결론으로 모인다.
    - **효율** — 순차 +1은 공짜, 점프는 비용(파이프라인 등). `if` 본문 X는 보통 "실행하려고" 쓴 흔한·중요 경로이므로, 흔한 경로(참→실행)를 공짜 흐름에 태우고 덜 흔한 경로(거짓→건너뛰기)에 점프 비용을 떠넘긴다.
    - **코드 레이아웃** — 소스에서 X는 조건 바로 아래에 온다. 그 시각적 순서를 기계어 순서와 일치시키려면 "본문으로 가기 = 순차 흐름", "건너뛰기 = 점프"가 자연스럽다.

### while — 되돌아가는 무조건 점프를 더한 것
```
L_cond: 조건 검사 → 플래그
        조건부 점프(거짓이면) → L_end   ; 탈출
        X 실행                          ; 본문
        무조건 점프 → L_cond            ; 위로 되돌아가 재검사
L_end:  ...
```
- **분기와 반복을 가르는 단 하나** = 본문 끝의 **위로 향하는 무조건 점프**. `if`엔 이게 없다. 반복을 만드는 건 정확히 이 한 줄이다.
- 역할 분담 — 조건부 점프 = 빠져나갈지 결정, 무조건 점프 = 무조건 다시 위로(반복의 본체).

### switch — 진입점 점프(점프 테이블) + fall-through
- switch의 본질은 조건을 하나씩 비교하는 게 아니라, **`x` 값으로 해당 case의 주소를 계산해 한 번에 점프**하는 것(점프 테이블). `else if`의 "1인가? 2인가?…" 순차 비교와 다르다.
- 그런데 switch는 **진입점(어디로 들어갈지)만 점프로 정하고 탈출은 안 정한다.** 일단 착지하면 PC가 평소처럼 +1로 흘러 **다음 case로 쏟아진다** — 이게 **fall-through**.
- **`break` = 그 탈출 점프**를 직접 박는 것. (`else if`는 컴파일러가 블록마다 "끝으로 가는 무조건 점프"를 자동으로 넣어줘서 상호 배타적이지만, switch는 그걸 안 해준다.)
- fall-through는 버그가 아니라 **의도된 기능** — 여러 case가 코드를 공유할 수 있다("여러 입구, 하나의 출구").
```c
case 'a': case 'e': case 'i': case 'o': case 'u':
    모음_처리();   // a~u 모두 여기로 흘러내려옴
    break;
```
- 대가는 `break` 누락 시 조용히 다음 case로 새는 **단골 버그**. (C 철학: 자동으로 막지 않는 대신 흘릴 자유를 준다, 책임은 프로그래머 — [[C 자료형 — 정수와 실수의 표현]]의 관통 대비.)

### goto — 점프의 직접 노출
- `goto`는 기계어 **무조건 점프를 고급 언어 표면에 그대로 노출**한 것. `if`/`while`이 점프를 정해진 패턴으로 포장·제한한 반면, `goto`는 포장을 벗겨 "아무 데로나"의 자유를 돌려준다.
- **남용 시 스파게티 코드** — 흐름이 사방으로 튀어 "이 줄에 어떤 경로로 도달했는가"를 추적 불가. 다익스트라 "Goto Considered Harmful"(1968)의 논거 = goto는 코드의 **정적 구조(텍스트 순서)와 동적 흐름(실행 경로)을 어긋나게** 만든다. → 순차/선택/반복 3구조만 쓰자는 **구조적 프로그래밍**의 계기.
- **그러나 규율 있는 goto는 정당하다.** C엔 `try-finally`(Java)나 소멸자/RAII(C++) 같은 "함수 탈출 시 자동 정리"가 없다. 자원을 여러 개 잡는 함수에서, 실패 지점마다 "그때까지 잡은 것만 역순 정리"를 깔끔히 하려면 **계단식 라벨 + fall-through 역이용**이 표준 관용구다.
```c
    if (파일 열기 실패)   return;
    if (메모리 할당 실패) goto fail_file;   // 파일만 정리
    if (락 걸기 실패)     goto fail_mem;    // 메모리+파일 정리
        ... 작업 ...
    락 풀기;
fail_mem:   메모리 해제;   // 여기 착지하면 아래로 줄줄 실행됨
fail_file:  파일 닫기;
    return;
```
- 이 goto는 **항상 앞으로, 항상 함수 끝 정리 구역으로만** 가므로 스파게티가 아니다(흐름 예측 가능). 리눅스 커널 등에서 활발히 쓰인다. "옛날 유물"이 아니라 "용처가 좁혀진" 것.

### do-while — 본문 최소 1회 보장
- 본질은 **"본문을 최소 한 번은 반드시 실행한다"**(조건을 본문 뒤에서 검사).
- **do-while을 부르는 신호 두 층위**
    - (전형적 신호) **초기 상태로는 조건을 판정할 수 없는 경우** — 예: 입력값을 받아야 비로소 검사할 게 생긴다. "한 번 실행해서 상태를 만든 뒤에야 조건 검사가 가능".
    - (상위 정의) 더 근본은 **"본문 1회가 로직의 본질인가"** — 메뉴 출력처럼 조건은 미리 판정 가능해도 "무조건 한 번은 보여줘야" 하는 경우까지 포함한다. 전형적 신호는 이 정의의 특수 케이스.
- **"따로 한 번 실행하고 while로 빼기"는 피한다.** 본문이 두 군데 중복되어 (1) 수정 시 양쪽을 똑같이 고쳐야 하는 DRY 위반, (2) "이 둘이 정말 같은 코드인가?"라는 독자의 인지적 의문을 부른다. do-while은 본문을 한 번만 쓰고 "최소 1회 + 반복" 의도를 한 덩어리로 표현한다.
- 단, do-while의 약점 — 조건이 **맨 아래**에 있어 긴 블록에선 "이게 반복문이었나"를 끝에서야 알게 됨(사람은 조건을 위에서 보는 데 익숙). 그래서 "최소 1회가 본질"인 자리에만 쓰고, 그 외엔 while/for가 읽기 좋다.

## 코드
```c
// do-while이 딱 맞는 자리: 입력 검증 (받아야 검사할 게 생김)
int n;
do {
    printf("1~10 입력: ");
    scanf("%d", &n);
} while (n < 1 || n > 10);

// switch fall-through를 의도적으로 쓰는 예
switch (c) {
    case 'a': case 'e': case 'i': case 'o': case 'u':
        vowels++;
        break;          // 이 break가 탈출 점프
    default:
        others++;
}
```

## 다른 언어에선?
- **switch 기본값** — break 누락 버그가 흔하자 후발 언어는 기본값을 뒤집었다. Go는 기본이 자동 탈출이고 흘리려면 `fallthrough`를 명시(C와 정반대). 자바의 화살표 `case x ->`는 fall-through를 아예 불가능하게 하고 여러 case 공유는 `case 1, 2, 3 ->` 콤마로 해결. 공통 전략 = **위험한 자동 흘림은 막고, 정작 필요한 'case 공유'는 별도 문법으로 남긴다**(위험은 버리고 쓸모는 남김).
- **자원 정리** — 함수 탈출 시 정리를 C는 수동(`goto` 관용구), C++은 자동(RAII·소멸자), Java는 `try-finally`/GC로 한다. C의 goto 정리 패턴은 이 자동 장치의 빈자리를 메우는 것 → [[메모리 관리 비교]]에서 본격화.

- **점프 테이블 세부** — switch가 값→주소를 실제로 어떻게 계산하는지, case가 듬성하거나(1, 100, 1000) 범위가 넓으면 테이블 대신 비교 연쇄로 컴파일되는지 등. 다음 패스.
