# C 자료형 — 정수와 실수의 표현

## 핵심 요약
> C의 자료형 크기는 하드웨어에 위임되어 정확히 안 박혀 있다(효율과 이식성). 정수는 2의 보수로 표현되어 범위가 비대칭이고 "최솟값 부호 뒤집기" 함정이 있다. 실수(부동소수점)는 유한한 비트로 무한한 실수를 욱여넣는 데서 두 종류의 한계, 곧 정밀도(가수) 한계와 진법 한계를 갖는다. 타입 간 형변환에서 올림/내림은 값이 아니라 타입 서열의 방향이며, 올림이어도 정보 손실이 날 수 있다(`int → float`).

## 내용

### 자료형 크기는 왜 정확히 정의되지 않나
- C 표준은 정확한 바이트 수를 안 박고 순서와 최소 크기만 정한다 (`char ≤ short ≤ int ≤ long ≤ long long`).
- 그 이유는 각 CPU가 자기가 가장 잘 다루는 크기를 쓰게 하려는 것. 크기를 비워둔 건 게으름이 아니라 이식성과 효율을 위한 의도적 설계.
- 양날의 검이다. 기계마다 크기가 달라 버그 온상이 될 수 있어서, 크기가 중요하면 `<stdint.h>`의 `int32_t`, `int64_t`(크기 못박은 타입)를 쓴다.

### 정수 — 2의 보수와 비대칭
- 정수 범위가 비대칭인 것(`int`은 `-2147483648 ~ +2147483647`로 음수가 1개 많음)은 2의 보수 때문이다.
- 메커니즘(4비트 예) — 최상위 비트가 부호를 결정한다(0이면 양수/0, 1이면 음수). 0이 양수 진영(`0000`)에 줄을 서서, 순수 양수는 7개, 음수는 8개가 된다.
- 최솟값 함정 — `-8`(4비트)은 있는데 `+8`은 없다. `-(-8)`을 계산하면 (비트 뒤집고 +1) 다시 `1000`(-8)이 된다. 부호를 뒤집어도 자기 자신.
    - 실제 `int`에서 `-(-2147483648)`은 여전히 `-2147483648`. 에러 없이 조용히 틀린 값이라, 절댓값 함수의 숨은 버그가 된다.

### 실수 — 부동소수점 비트 구조
- float(4바이트)은 `[부호 1][지수 8][가수 23]` 순서다.
    - 부호가 맨 앞인 이유 — 부호-크기 표현(sign-magnitude). 부호는 크기와 독립적인 정보라 따로 떼둔다(사람이 `-3.0` 쓰는 방식). 2의 보수가 아니라서 `2.0`과 `-2.0`은 부호 비트 1개만 다르다.
    - 지수가 가수보다 앞인 이유 — 양수끼리는 비트패턴을 정수로 통째 비교해도 대소가 맞도록 하기 위함(지수에서 갈리면 가수는 볼 필요 없음, 곧 사전식 비교).
- "부동(浮動)"은 소수점 위치가 움직인다는 뜻. 지수가 소수점을 움직인다. (예: `1.5 × 2^3` vs `1.5 × 2^-2`)

### 실수 — 오버플로와 언더플로
- 둘 다 지수부(8비트)의 한계 때문이며, 정수와 양상이 다르다.
- 오버플로(너무 큼, 약 `3.4e38` 초과) — 정수처럼 wrap 되지 않고 `inf`(무한대)라는 전용값이 된다. 전염된다(`inf + 1 = inf`).
- 언더플로(0에 너무 가까움, 약 `1.2e-38` 미만) — 표현하지 못해 `0`으로 뭉개진다. 그 0으로 나누면 `inf`나 `NaN` 폭탄이 된다.

| | 오버플로 | 언더플로 |
|---|---|---|
| 정수 | wrap(음수로 순환) | 개념 없음 |
| 실수 | `inf` | `0`으로 뭉개짐 |

### inf 와 NaN (곁가지 — 다익스트라 등 응용)
- `inf`는 오버플로나 `5.0/0.0`(0 아닌 수 ÷ 0)에서 나온다. 비교가 정상 작동한다(`inf`는 모든 실수보다 큼). 다익스트라의 "무한대 거리"에 쓸 수 있으나 `inf - inf = NaN`을 주의해야 한다.
    - 실무에선 거리가 정수일 때 `inf`보다 "충분히 크되 오버플로 여유 있는 정수"(예: `1e9`)를 INF로 쓴다. `INT_MAX`를 INF로 쓰면 거기 뭐만 더해도 오버플로되어 음수로 wrap된다.
- `NaN`(Not a Number)은 정의 불가 연산의 결과다. `0.0/0.0`, `inf-inf`, `inf/inf`, `0*inf`, `sqrt(-1)`, `log(-1)` 등.
    - 악명 높은 성질 — 자기 자신과도 같지 않다(`x == x`가 false). 그래서 비교 기반 로직(정렬, 탐색)이 조용히 붕괴한다.
    - NaN 검사 트릭은 `if (x != x)`이며 참이면 NaN이다. (보통은 `isnan()` 사용)
- NaN vs SQL의 NULL — "비정상 표식 + 전염성"이라는 점에서 사촌이다. 단 NaN은 2값 논리의 '자기와도 다른 거짓'이고, NULL은 3값 논리의 '알 수 없음(unknown)'이라 검사법도 다르다(`!=` vs `IS NULL`).

### 실수 — 두 종류의 오차 (진법 한계가 더 근본적)
- 현상 A, 삼켜짐(absorption) — `(1.0e20 + 5.0) - 1.0e20 = 0`. 원인은 가수부 정밀도(자릿수) 한계다. 큰 수에 작은 수를 더하면 작은 게 유효숫자 밖으로 밀려 사라진다. 진법과 무관하다(10진법 계산기도 발생).
- 현상 B, 진법 한계 — `0.1 + 0.2 ≠ 0.3` (`0.30000...004`). 원인은 2진법이 0.1을 정확히 표현하지 못하는 것이다.
    - 유한소수 조건 — 분수가 어떤 진법에서 유한소수이려면 분모의 소인수가 그 진법 밑의 소인수여야 한다.
        - 10진법(밑 2×5)은 분모가 2, 5로만 이루어지면 유한. `1/3`은 3 때문에 무한.
        - 2진법(밑 2)은 분모가 2로만 이루어져야 유한. `1/10`은 5 때문에 2진법에서 무한소수가 되어 잘리며 오차가 생긴다.
    - 진법이 다르면 "깔끔한 수"의 집합이 다르다. 0.1은 10진법 눈엔 깔끔하지만 2진법 눈엔 `1/3`처럼 지저분하다.
- 정수 vs 실수, 한계의 성격이 다름
    - 정수는 범위 밖에서만 문제가 생긴다(오버플로). 범위 안은 완벽하다. "울타리 친 완벽한 땅."
    - 실수는 범위 안에서도 곳곳이 부정확하다(`0.1`). "넓지만 구멍 뚫린 땅."
    - 그래서 진법 오차(실수 내부의 구멍)가 범위 넘침(정수의 경계 문제)보다 더 은밀하고 까다롭다. 진법 오차는 소수부를 가진 실수의 고유 문제다(정수엔 소수부가 없어 없음).
- 실전 수칙 — 실수는 `==`로 비교하지 말고 `fabs(a-b) < 1e-9` 같은 epsilon 비교를 쓴다. 돈 계산에 float/double을 쓰지 않는다(정수 센트 단위 또는 십진 전용 타입).

### short 와 char
- short(보통 2바이트)는 현대 PC에선 거의 안 쓴다. 메모리도 안 아쉽고 속도 이득도 없다(`int`가 그 CPU에 가장 자연스러움). 살아남는 곳은 대량 데이터(오디오 16비트 샘플 수백만 개), 규격 고정(파일/네트워크 포맷, 이때도 `int16_t` 권장), 임베디드다.
- char는 본질이 "1바이트 정수"다. 문자는 그 위에 아스키표를 씌운 해석일 뿐이다. `'A' == 65`이고, `%d`로 보면 65, `%c`로 보면 'A'다(텍스트/바이너리의 "해석 약속"과 동일).
    - 정수라서 문자 산술이 가능하다. 대소문자 변환(`'c' - 32`), 문자에서 숫자로(`'7' - '0' == 7`).
    - 의도(문자) vs 정의(정수) — 설계 의도는 문자에서 출발했으나, 메모리가 귀하던 시절 "전용 타입 대신 1바이트 정수를 겸용"하는 설계를 택해 정의상 정수 타입이 되었다. "아스키 때문에 정수로 쓸 수 있는" 게 아니라 "정수로 만들었기에 아스키 산술이 가능"한 것이다.

### 형변환 — 올림/내림은 타입 서열이다
> [!info] 추가 절 · 2026-06-17 · 출처 [[프로그래밍 기초 문법_ C ver]]

- **올림/내림의 기준은 "값"이 아니라 "타입의 서열(rank)"이다.** 변환 대상 타입이 서열에서 위에 있으면 올림(promotion), 아래면 내림(demotion). 값이 무엇이든 무관하다.
    - 서열(대략): `int < unsigned < long < long long < float < double < long double`.
    - ⚠️ 이 일직선은 직관용 단순화다. 엄밀히는 (1) `unsigned`와 `long`의 상대 위치가 **플랫폼 의존**이고(long이 int보다 큰지 같은지에 따라 갈림), (2) 정수 순위(integer rank) 체계와 부동소수점은 **별도 규칙**으로 다뤄진다. 여기선 "더 넓은 폭의 타입으로 가면 올림"이라는 큰 방향만 잡는다. 정밀 규칙은 막힌 것 참조.
    - `int → float`은 float이 위 서열이라 **올림**이다. `10`이 `10.0`이 되는 것은 결과의 모양일 뿐, 올림인 *이유*가 아니다. (원본글 질문 "10→10.0이 어째서 올림이냐"의 답.)
- **흔한 오해 — "정보(자리수)가 생기면 올림, 잘리면 내림".** 틀렸다. 그게 기준이면 같은 `int → float`이 값에 따라 올림이었다 내림이었다 해야 하는데(`10`은 그대로, `16777217`은 손실), 같은 변환의 분류가 값마다 바뀔 수는 없다.
- **정보 손실은 올림/내림과 별개의 축이다.** 보통 올림은 안전하지만, 항상 그렇지는 않다.

| 변환 | 방향(타입 서열) | 정보 손실 |
|---|---|---|
| `int → double` | 올림 | 없음 (안전) |
| `int → float` | **올림** | **있을 수 있음** |
| `double → int` | 내림 | 거의 항상 (소수부 버림) |

- **`int → float`이 올림인데도 정보가 새는 이유** — float의 정수 정밀도는 가수 `23+1 = 24`비트뿐이다(위 "부동소수점 비트 구조" 참조). `2^24`(16,777,216)까지는 1칸씩 빠짐없이 표현하지만 그 위는 2칸·4칸씩 띄엄띄엄 건너뛴다. 그래서 `2^24 + 1`은 표현 칸에 없어 가장 가까운 `2^24`로 뭉개진다.
    - 두 관점이 갈린다. **범위(range)** — float은 지수 8비트 덕에 int보다 훨씬 큰 수까지 닿는다(올림인 이유). **정밀도(precision)** — float의 정수 표현력은 24비트뿐이라 int(32비트 전부 정수)보다 촘촘함이 떨어진다(정보가 새는 이유). 같은 32비트를 *어디에 쓰느냐*의 차이다: float은 멀리 가는 능력과 촘촘함을 맞바꿨다.
    - 반면 `double`은 가수가 `52+1 = 53`비트라 32비트 int를 통째로 담고도 남는다. 그래서 `int → double`은 안 새고 `int → float`만 샌다.
- 명시적 형변환(캐스팅)은 그 식에서만 일시적으로 타입을 바꾸는 것이지 변수 자체를 영구히 바꾸지 않는다.

## 코드
```c
// 정수 최솟값 함정
int x = -2147483648;
int y = -x;            // +2147483648이 없음, 여전히 -2147483648

// 실수 비교는 epsilon으로
if (fabs((0.1 + 0.2) - 0.3) < 1e-9) { /* 같다고 판정 */ }

// NaN 검사
if (v != v) { /* v는 NaN */ }

// char는 정수
char upper = 'c' - 32;   // 'C'
int  num   = '7' - '0';  // 7

// 형변환 — 올림이어도 정보가 샐 수 있다
float  f = 16777217;   // 2^24+1 → 16777216.0 (올림인데 손실)
double d = 16777217;   // 정확 (double 가수 53비트)
```

## 다른 언어에선?
- 자료형 크기 — 자바는 `int`가 어디서든 무조건 32비트다. JVM(가상 기계)이 하드웨어 차이를 흡수하니 크기 통일이 가능하다. C는 하드웨어 밀착(효율), 자바는 통일(이식성과 단순함).
- 2의 보수, 최솟값 함정, 부동소수점(inf·NaN·0.1 오차)은 자바도 동일하다. 둘 다 IEEE 754와 2의 보수라는 하드웨어 레벨 약속을 공유하기 때문. 자바도 `Math.abs(Integer.MIN_VALUE)`가 음수이고 `Double.NaN != Double.NaN`이 참이다. 돈 계산용으로 `BigDecimal`을 표준 제공한다.
- 형변환 — `int → float`의 정밀도 손실은 자바도 동일하다(IEEE 754 공유). 단 자바는 손실 가능한 내림(예: `int → byte`)에 **명시적 캐스트를 강제**해 실수를 줄인다. C는 암묵 변환을 폭넓게 허용한다(자유 vs 안전의 그 대비).
- char는 큰 갈림길이다. 자바 `char`는 정수가 아니라 진짜 문자 타입에 가깝고 2바이트(유니코드)다. C는 "char는 작은 정수, 알아서 써"(자유), 자바는 "문자와 숫자 섞으면 헷갈리니 분리"(안전). 1바이트(아스키) vs 2바이트(유니코드)는 추후 문자 인코딩 비교로 이어진다.
- 관통하는 대비 — C는 힘과 자유를 주되 책임은 프로그래머에게, Java는 안전과 규율을 주되 위험한 도구는 제거한다(`#define` 제거, char 분리, 암묵 내림 차단 등에서 반복).

## 막힌 것 / 의문
- 자동 형변환의 세부 분류(정수 승격, 대입 변환, 수식의 일반 산술 변환)와 정수 순위(integer rank)의 정밀 규칙은 이번 패스에서 개념(올림/내림 = 타입 서열)까지만 정리. 세부 규칙은 다음 패스.
