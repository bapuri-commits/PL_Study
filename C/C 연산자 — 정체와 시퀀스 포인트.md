# C 연산자 — 정체와 시퀀스 포인트

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 문법_ C ver]]의 토론에서 파생되었습니다. (2026-06-17)

## 핵심 요약
> 두 줄기가 흐른다. (1) **"생긴 것 ≠ 정체"** — 콤마는 한 기호에 두 정체(연산자/구분자)가 있고, sizeof·_Alignof는 함수처럼 생겼지만 컴파일타임 연산자다. 타입에서 바로 나오는 정보(크기·정렬)는 컴파일타임 상수라 배열 크기 자리에 들어간다. 그 반대편이 런타임에 크기가 정해지는 VLA다. (2) **시퀀스 포인트** — 전위/후위의 부수효과가 반영되는 시점은 시퀀스 포인트까지 보장되지 않아서, 한 시퀀스 포인트 안에서 같은 변수에 접근이 충돌하면 미정의 동작이 된다.

## 내용

### 콤마 — 한 기호, 두 정체
- C에는 같은 `,` 기호가 **두 가지 역할**로 쓰인다. 헷갈림의 근원이 여기다.
    - **구분자(separator)** — 단순히 항목을 나열한다. 연산자가 아니다.
        - 선언의 변수 나열 `int a = 1, b = 2;`
        - 함수 인자 목록 `foo(a, b);`
        - for문 초기화 나열 `for (i=0, j=9; ...; )`
    - **콤마 연산자(operator)** — `x = (a, b)`. "왼쪽을 평가하고 → 그 값을 버리고 → 오른쪽을 평가해 그 값을 전체 결과로 내놓는다."
- 연산자 콤마의 핵심 성질: **그 자체가 시퀀스 포인트**다. 왼쪽의 부수효과가 오른쪽 평가 전에 반드시 반영된다(아래 미정의 동작 절에서 결정적으로 작용).

### sizeof — 함수의 탈을 쓴 컴파일타임 연산자
- `sizeof(...)` 모양 때문에 함수로 착각하기 쉽지만 **연산자**다. 근거 둘.
    1. **피연산자를 (보통) 실행하지 않는다.** `sizeof(x++)` 뒤에도 `x`는 그대로다(증가 안 됨). sizeof는 x++의 *값*이 아니라 *타입*만 보기 때문. 타입은 실행 없이 컴파일타임에 알 수 있으므로, 코드를 돌리지 않고 타입만 분석하고 끝낸다. (함수라면 인자를 실제 평가해 넘기므로 `foo(x++)`는 반드시 x를 증가시킨다.)
    2. **괄호 없이도 쓸 수 있다.** `sizeof 10`, `sizeof x`처럼 식(expression)에는 괄호를 생략할 수 있다. 단항 `-`가 `-10`처럼 피연산자에 붙는 것과 같다. 함수 호출은 괄호가 문법적 필수라 `foo 10`이 불가능한 것과 대비된다.
- 결과는 **대개 컴파일 중에 상수로 박힌다.** 그래서 배열 크기 자리에 넣을 수 있다(`int arr[sizeof(int)*2];`). 배열 크기는 컴파일타임에 정해져야 하는 자리인데, sizeof 식은 그 시점에 이미 확정되므로 문제없다.

> [!warning] 단 하나의 예외 — VLA에 쓴 sizeof
> "sizeof는 항상 컴파일타임 상수, 피연산자를 실행 안 함"에는 **예외가 하나 있다: 피연산자가 VLA(가변 길이 배열)일 때.** `int vla[n];` 뒤의 `sizeof(vla)`는 `n * sizeof(int)`를 **런타임에** 계산한다(크기가 런타임 값 n에 달렸으니 당연). 즉 VLA의 sizeof만은 컴파일 상수가 아니고, 그 경우엔 크기 결정을 위해 런타임 평가가 일어난다. (VLA는 아래 컴파일타임/런타임 절 참조.)

> [!tip] 타입 이름엔 괄호가 강제되는 이유
> 식(`x`, `10`)은 괄호 없이도 파싱이 명확하지만, **타입 이름**(`int`)을 날것으로 두면 캐스트 등과 충돌한다. 예: `sizeof (int) * p`는 괄호 규칙이 없으면 `(sizeof(int)) * p`(곱셈)인지 `sizeof((int)*p)`(`*p`를 int로 캐스트)인지 모호하다. 타입 이름을 괄호로 감싸도록 강제해 피연산자 경계를 못 박아 이 모호함을 없앤다. 그래서 `sizeof(int)`는 함수처럼 보이지만 괄호는 호출 괄호가 아니라 경계 표시다.

### _Alignof — 정렬, 그리고 또 하나의 컴파일타임 연산자
- 먼저 **정렬(alignment)**. CPU는 메모리를 1바이트씩 임의 주소에서 집지 못하고, **워드 블록 단위**(예: 4바이트 머신이면 `[0~3] [4~7] [8~11]…`, 경계가 고정)로만 읽는다.
    - **정렬된 경우** — 4바이트 `int`가 주소 4에 있으면 블록 `[4~7]`에 통째로 들어가 **읽기 1회**로 끝난다.
    - **어긋난 경우** — 주소 2에 있으면 `[0~3]`의 끝 2바이트 + `[4~7]`의 앞 2바이트에 **걸쳐서**, 블록 두 개를 읽어 추리고 합쳐야 한다(느림). 일부 CPU는 아예 거부하고 하드웨어 폴트로 죽는다(크래시).
    - 그래서 하드웨어는 타입마다 "시작 가능한 주소의 배수"를 요구·선호한다. `int`는 보통 4의 배수, `char`는 1(아무 데나 OK).
- **`_Alignof(타입)`** = 그 타입이 시작해도 되는 주소의 배수(`_Alignof(int)` → 보통 4, `_Alignof(char)` → 1).
- **`_Alignas(N)`** = 변수를 N의 배수 주소에 강제 배치하라는 지정.
- sizeof와 같은 부류 — **타입에서 바로 나오는 정보는 컴파일타임 상수**다. `_Alignof(int)`의 값은 컴파일 대상이 정해진 순간 확정되므로 런타임에 알아낼 필요가 없고, 배열 크기 자리 등에 쓸 수 있다. (sizeof의 VLA 예외와 달리, _Alignof는 타입에만 적용되므로 늘 컴파일 상수다.)
- (C11 도입. C23/C++에선 `alignof`/`alignas`로 키워드가 정리됨.)

### 전위·후위와 시퀀스 포인트 — 미정의 동작의 뿌리
- 전위/후위에는 **두 개의 다른 순서**가 섞여 있다. 이를 분리해야 한다.
    - **축 1 — 값을 내놓는 순서.** 전위 `++x`는 "올리고 그 새 값을 건넨다"(선증가 후사용), 후위 `x++`는 "현재 값을 건네고 그 다음 올린다"(선사용 후증가).
    - **축 2 — 부수효과(+1)가 실제로 반영되는 시점.** C 표준은 "이 시점에 즉시"라고 정하지 않고, **시퀀스 포인트(sequence point)까지 언젠가** 반영하면 된다고만 한다. 문장 끝(`;`), 콤마 연산자, `&&`/`||` 등이 시퀀스 포인트다.
- **미정의 동작(undefined behavior)의 진짜 기준** — "증감 연산자가 몇 개냐"가 아니다. **한 시퀀스 포인트 안에서, 같은 변수를 수정(write)하면서 다른 곳에서 읽거나(read) 또 수정하는 접근이 충돌**하면 미정의다. 미정의는 "틀린 값"이 아니라 "표준이 결과를 보장하지 않음"(컴파일러마다 다르거나 깨질 수 있음)을 뜻한다.
    - **단, 읽기가 "저장할 값을 계산하기 위한" 것이면 충돌이 아니다.** `x = x + 1`은 안전하다 — x를 읽어 새 값을 만들고 그 값을 x에 한 번만 쓴다(읽기와 쓰기가 한 흐름). 충돌은 그 수정과 **무관한 별개의 접근**이 같은 변수에 겹칠 때다.
    - `y = x++ + x++;` — 한 문장 안에서 x를 두 번 수정. 충돌 → **미정의.**
    - `y = x++ + x;` — 증감은 하나지만 한 문장 안에서 x를 수정(`x++`)하면서, 그와 무관한 읽기(`+ x`)도 한다. 오른쪽 x가 증가 전 값인지 후 값인지 미정 → **미정의.** (증감 개수가 기준이 아님을 보여주는 핵심 예.)
    - `y = x++; z = x++;` — 세미콜론이 사이에 시퀀스 포인트를 찍어, 각 문장 안에서는 x를 한 번씩만 건드린다 → **안전.**
    - `a = x++ + y++;` — x와 y는 다른 변수라 충돌 대상이 없다 → **안전.**
    - `c = (x++, x++);` — 콤마 연산자가 사이에 시퀀스 포인트를 찍어 각 `x++`를 격리한다 → **안전.**

> [!note] C11 이후의 정식화
> "시퀀스 포인트"는 C11에서 **sequenced-before**라는 더 정밀한 순서 관계로 재정식화됐다(어느 연산이 어느 연산보다 먼저 순서지어지는가를 짝으로 규정). 교육적으로는 시퀀스 포인트 프레임이 직관적이라 이 노트에선 그대로 쓴다.

### 컴파일타임 vs 런타임, 그리고 VLA
- **컴파일타임/런타임은 "시간대"**다. 컴파일타임 = 기계어로 번역하는 동안(아직 안 돎), 런타임 = 실행 파일이 실제로 도는 동안.
- 배열 크기는 **항상 컴파일타임에 정해지는 게 아니다.** 크기 값의 *출처*에 따라 자리를 잡는 *시점*이 갈린다.
    - `int a[sizeof(int)*2];` — 크기가 **컴파일타임 상수**. 번역 중에 스택 자리가 확정된다.
    - `int b[n];` (n은 런타임 입력값) — **VLA(가변 길이 배열, C99)**. 그 줄을 실행하는 순간 크기가 정해진다. 실행마다 크기가 달라질 수 있다. (그래서 `sizeof(b)`도 런타임 평가 — 위 sizeof 예외.)
- VLA의 위험 — 크기가 컴파일러 통제를 벗어나 런타임 값(예: 사용자 입력)에 달리면, 음수거나 지나치게 크면 **런타임에 스택이 터진다**(스택 오버플로). 그래서 C11에서 **선택(optional) 기능으로 강등**됐고, 실무에선 동적 크기가 필요하면 `malloc`으로 **힙에** 잡아 실패를 `NULL`로 잡아내는 쪽을 권장한다.
- 이는 [[C 자료형 — 정수와 실수의 표현]]에서 정리한 관통 대비("C는 자유를 주되 책임은 프로그래머에게")의 또 다른 사례다.

## 코드
```c
// 콤마 — 두 정체
int a = 1, b = 2;     // 구분자(나열)
foo(a, b);            // 구분자(인자 목록)
int x = (a, b);       // 연산자: a 평가·버림 → b가 결과 (x == 2)

// sizeof — 피연산자를 실행하지 않음 / 괄호 생략 가능
int n = 5;
size_t s = sizeof(n++);   // n은 여전히 5 (실행 안 됨, 타입만 봄)
int t = sizeof 10;        // 괄호 없이 식에 붙음 — OK (연산자라서)
int arr[sizeof(int)*2];   // 컴파일타임 상수 → 배열 크기로 사용 가능

// 시퀀스 포인트와 미정의 동작
int i = 1;
i = i + 1;            // 안전: 읽기가 '저장할 값 계산용'이라 충돌 아님
// int u = i++ + i++;   // 미정의: 한 문장에 i 수정 2회
// int v = i++ + i;     // 미정의: 수정(i++) + 무관한 읽기(i) 충돌 (증감 1개여도)
int p = i++;  int q = i++;   // 안전: 세미콜론이 시퀀스 포인트
int w = (i++, i++);          // 안전: 콤마 연산자가 시퀀스 포인트

// VLA — 런타임에 크기 결정 (위험)
int m;
scanf("%d", &m);
int vla[m];               // m이 음수/거대값이면 런타임 스택 오버플로
size_t sz = sizeof(vla);  // 이 sizeof는 런타임에 m*sizeof(int) 계산 (예외)
```

## 다른 언어에선?
- **콤마 연산자** — 자바엔 콤마 *연산자*가 없다. 콤마는 for문 초기화/증감 등 정해진 자리의 구분자로만 쓰인다("위험·혼란 제거" 철학, [[C 문법 조각 — 왼값·오른값과 scanf 경고]]의 `#define` 제거와 같은 결).
- **sizeof** — 자바엔 sizeof가 없다. 타입 크기가 스펙으로 고정돼 있어(`int`는 어디서나 32비트, [[C 자료형 — 정수와 실수의 표현]] 참조) 굳이 물어볼 필요가 없기 때문. C는 하드웨어 위임이라 sizeof로 물어야 한다.
- **미정의 동작** — `i++ + i++` 같은 식이 C에선 미정의지만, 자바는 평가 순서를 **왼쪽→오른쪽으로 강제**해 결과가 정의된다. C가 컴파일러 최적화 여지를 위해 순서를 풀어둔 반면, 자바는 못 박아 이식성·예측가능성을 택했다.
- **VLA / 동적 배열** — 자바 배열은 항상 런타임에 힙에 생성되고(`new int[n]`), 크기 음수면 예외(`NegativeArraySizeException`)로 즉시 차단한다. C의 VLA가 스택에서 조용히 터지는 것과 대비. (메모리 관리 비교에서 본격화.)

## 막힌 것 / 의문
- **정적/동적 바인딩** — 컴파일타임/런타임(시간대) 위에서 "이름↔대상 묶기가 언제 확정되나"의 문제. 정적=컴파일타임 확정(C 함수 호출), 동적=런타임 확정(C++ `virtual`). 후자는 OOP·다형성 영역이라 여기선 연결만 하고 보류 → [[Questions/_질문 인덱스]] 참조.
- 원본글의 **단축 계산(`&&`/`||`)**, **연산자 우선순위**는 이 노트 범위에서 다루지 않음(다음 패스). `&&`/`||`가 시퀀스 포인트라는 점에서 이 노트와 이어짐.
- **비트 연산**(원본글 질문1-4)은 별도 노트 [[C 비트 연산]]으로 분리 예정.
