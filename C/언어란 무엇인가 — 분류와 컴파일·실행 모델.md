# 언어란 무엇인가 — 분류와 컴파일·실행 모델

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 개념_ C ver]]의 토론에서 파생되었습니다. (2026-06-17)

## 핵심 요약
> 저급에서 고급 언어로의 흐름은 추상화를 한 겹씩 끼워 넣은 역사다. 각 층은 아래층의 복잡함을 숨기고 사람에게 편한 표면만 노출한다. 컴파일은 이 추상(이름과 구조)을 기계의 실체(주소와 기계어)로 풀어내는 과정이며, 그 과정에서 정보를 버리기 때문에 되돌릴 수 없다.

## 내용

### 언어의 계층과 추상화
- 기계어에서 어셈블리어, 고급언어로 가는 흐름은 추상화 계층을 쌓아 올린 역사다.
    - 어셈블리어 — 2진수 비트열을 숨기고 `MOV`, `ADD` 같은 기호로 가림.
    - 고급언어 — 특정 CPU의 레지스터와 명령어를 숨기고 `x = a + b` 같은 표현으로 가림.
- 추상화의 본질은 "내부는 숨기고 쓰기 좋은 표면만 보여준다"는 것. 함수, 파일시스템, OS도 모두 같은 패턴.
- 단, 추상화는 공짜가 아니다. 한 겹 쌓을 때마다 보통 성능과 제어력을 조금씩 내준다. C가 살아남은 이유가 추상화를 얇게 유지해 하드웨어에 가깝기 때문.

### 기계어와 어셈블리어가 불편한 이유
- 어셈블리는 CPU의 원시 동작을 하나하나 사람이 지시해야 한다.
    - 레지스터를 직접 관리한다 (`mov`로 값 옮기고 계산하고 다시 빼냄).
    - "더한다" 하나도 불러오기, 더하기, 저장하기로 쪼개야 한다.
- 기계어는 거기에 "사람이 못 읽는 2진수"라는 벽까지 더해진다.
    - 읽기 거의 불가, 수정 시 모든 주소 재계산, 오타가 침묵의 재앙(컴파일러처럼 잡아주는 게 없음).
- 둘 다 하드웨어에 종속된다(특정 CPU에서만 유효). 다른 CPU로 옮기면 새로 작성해야 한다.

### 컴파일은 실제로 어떻게 진행되나
> 핵심 — 기계어는 이름이 아니라 "주소(위치)"로 식별한다. 식별자 이름이 기계어로 변환되는 게 아니다.

1. 어휘 분석(쪼개기) — 소스를 토큰으로 분해. `int x = 20;` 는 `int`, `x`, `=`, `20`, `;` 로 나뉜다.
2. 구문 분석(구조 파악) — 토큰을 문법에 맞는 트리로 조립. 여기서 문법과 철자 오류가 잡힌다.
3. 이름을 주소로 치환 — 심볼 테이블을 만들어 각 변수에 메모리 주소를 배정한다(`x` 를 `0x1000` 으로). 코드 속 이름을 전부 주소로 치환. 이 단계에서 이름이 죽고 주소가 태어난다. 표는 컴파일이 끝나면 버려져서, 기계어에 이름이 안 남는다.
4. 코드 생성 — 트리와 주소로 실제 기계어 명령을 생성한다. 오브젝트 파일(.obj)이 나온다.
5. 링크 — 오브젝트 파일과 라이브러리를 합쳐 실행 파일을 생성한다. 다른 파일의 함수(`printf` 등) 위치를 찾아 연결한다.

- 비유 — 컴파일러는 "철수네 집"(이름)을 "○○동 ○○호"(주소)로 번역하고 자신은 빠진다. 기계는 주소만 보고 일한다.

### 텍스트 파일 vs 바이너리 파일
- 모든 파일은 결국 0과 1. 차이는 "바이트를 문자 인코딩으로 해석하기로 약속했는가"이다.
    - 텍스트 파일은 바이트를 아스키나 유니코드 문자표로 읽기로 약속된 파일. 사람이 읽을 수 있고 아무 에디터로나 열린다. (`.c`, `.txt`, `.md`, `.html`)
    - 바이너리는 문자표로 해석하면 안 되는 파일(`.exe`, `.jpg`). 메모장으로 열면 깨진다.
- 소스 파일(`.c`)이 텍스트인 이유가 이것. 오브젝트 파일과 실행 파일은 바이너리.
- `.docx`는 "텍스트를 담은 바이너리 컨테이너"다. 알맹이(XML)는 텍스트지만 ZIP으로 압축된 포장은 바이너리. 그래서 통째로 메모장에 열면 깨진다. (LLM이 docx를 읽을 때도 ZIP을 풀어 안의 XML을 파싱한다.)

### 컴파일은 왜 역변환이 안 되나
- 압축(`.zip`)은 무손실 변환이다(정보 안 버림, 완벽 복원). 컴파일은 정보를 버리는 변환이다.
- 버려지는 것 — 변수 이름(주소만 남음), 주석(통째로 버림), 코드 구조(for/while 구분, 함수, 들여쓰기 다 사라짐).
- 비유 — 소를 갈아 패티를 만드는 것. 갈리며 구조 정보가 사라져 복원 불가.
- 비가역은 컴파일만의 특성이 아니다. JPEG 압축(손실), 해시 함수, 반올림 등 "정보를 버리면 못 돌아간다"는 일반 원리의 한 사례다.
- 디컴파일러는 기계어를 거꾸로 분석하지만 원본 복원이 아니다. 버려진 이름과 주석은 못 살려서 `var1`, `sub_401000` 같은 무의미한 이름으로 채워진 "동작만 비슷한" 코드가 나온다.
- 그래서 소스는 목숨처럼 보관하고(잃으면 끝), 게임은 실행 파일만 판매한다(소스는 영업비밀이라 보호). 비가역성이 여기선 보호 장치로 작동한다.

## 코드
> 같은 동작 `c = a + b`의 층위별 비교.

```asm
; 어셈블리 (x86 느낌)
mov eax, [a]    ; a를 레지스터에 복사
add eax, [b]    ; b를 더함
mov [c], eax    ; 결과를 c에 저장
```

```c
// 고급언어
c = a + b;
```

## 다른 언어에선?
> C/C++ vs Java의 컴파일·실행 모델. 핵심 비교축이라 추후 Comparisons에서 본격화.

- C/C++는 소스를 그 기계의 기계어로 직접 번역한다(AOT). 결과물(`.exe`)이 플랫폼마다 다르므로 플랫폼별 재컴파일이 필요하다. 빠르지만 플랫폼에 종속된다.
- Java는 소스를 바이트코드(`.class`)로 컴파일한다. 이건 실제 CPU 명령이 아니라 가상 CPU(JVM)용 명령이다.
    - 결과물(`.class`)은 어디서나 동일하고, 대신 그걸 실행하는 JVM이 플랫폼마다 다르게 깔린다. ("Write Once, Run Anywhere")
    - 플랫폼 차이를 흡수하는 책임이 컴파일 결과물에서 JVM으로 넘어간다.
    - 실행 방식은 처음엔 인터프리터(한 줄씩 해석, 느림)로 시작해, 자주 쓰는 부분은 JIT 컴파일로 실행 중에 기계어로 번역하고 캐싱한다(네이티브 속도). "자바는 인터프리터 언어"라는 말은 반만 맞다.
- 세 갈래 정리 — C/C++(AOT, 빠름·종속), 순수 인터프리터(유연·느림), Java(바이트코드 + JVM + JIT, 독립·준수한 속도).
