# C++ 헤더와 `#include` — 복붙·선언·구현·표준화

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 개념_ C++ ver]]의 토론에서 파생되었습니다. (2026-06-18)

## 핵심 요약
> `#include`는 전처리기의 **단순 텍스트 복붙**이다(`#define`과 같은 결). 헤더엔 대부분 **선언**만 들어온다 — 컴파일러는 그 선언으로 타입을 검사하고 **빈칸(미해결 심볼)을 남긴 기계어**를 만들고, **링커**가 미리 컴파일된 표준 라이브러리의 **실제 구현 주소로 빈칸을 채운다**. "복잡함"은 전처리가 아니라 컴파일·링크가 선언/구현을 따로 처리하다 합치는 데 있다. 확장자 없는 헤더(`<iostream>`)는 C++이 표준화하며 `std::`에 넣은 정식판이라는 **표식**이고, `.h`는 C 유산이다. C 기능의 C++판은 `c` 접두사 버전(`<cstdio>`).

## 내용

### `#include`는 "파일 복붙"이다
- `#define`이 전처리 단계의 "글자 갈아치우기"였듯([[C 문법 조각 — 왼값·오른값과 scanf 경고]]), `#include`는 **같은 전처리기**가 하는 "파일 통째 복붙"이다. `<iostream>` 파일을 찾아, `#include`라고 쓴 **바로 그 줄 자리에** 그 내용을 텍스트로 그대로 붙인다. (보통 파일 맨 위에 `#include`를 모아두니 결과적으로 "위에 붙는" 것처럼 보일 뿐, 실제론 그 줄에 꽂힌다.)
- 컴파일러는 이 복붙이 끝난 결과물만 본다. 그래서 컴파일러 입장에선 "그 코드가 원래 여기 다 적혀 있던 것처럼" 보인다.
- 즉 전처리 자체는 **어이없이 단순**하다. 복잡함은 그 뒤에 있다.

### 선언 vs 정의 — 헤더엔 선언만 온다
- 용어가 직관과 반대로 붙어 헷갈리기 쉽다.
    - **선언(declaration)** — "이런 게 존재한다"는 통보. 이름·타입·시그니처만. 몸통(실제 코드) 없음.
    - **정의(definition)** — 실제 알맹이(함수 몸통, 진짜 구현).
- `<iostream>`이 복붙해주는 건 **대부분 선언**이다. "`cout`이라는 게 있고 `<<`는 이런 타입을 받는다"는 통보지, "화면에 글자를 어떻게 찍는지"의 구현이 아니다.
- 실제 구현(정의)은 헤더에 안 따라온다. **미리 컴파일된 표준 라이브러리** 안에 들어 있다.
    - ⚠️ **예외 — 템플릿.** `vector`처럼 템플릿으로 된 것은 구현이 **헤더에 들어간다.** 템플릿은 쓰는 자리에서 타입별로 코드를 찍어내야 하므로([[C++이란 무엇인가 — OOP 편한 C를 넘어서]]의 컴파일타임 생성), 컴파일러가 그 시점에 구현 전체를 볼 수 있어야 하기 때문. (자세히는 다음 패스 / [[제네릭·템플릿 비교]].)

### 컴파일과 링크 — 빈칸을 남기고, 나중에 채운다
- 헤더가 선언만 주는데 어떻게 프로그램이 도나? 일이 **두 시간대로 쪼개진다.**
    - **컴파일** — 선언만 보고도 "`cout << "hi"`는 문법·타입이 맞다"를 검사하고 기계어로 번역한다. 단 `cout`의 *진짜 주소*는 아직 모르니 **"여기 누군가 들어올 자리"라는 빈칸(미해결 심볼)**으로 남긴다.
    - **링크** — 그 빈칸을, 미리 컴파일된 표준 라이브러리 안의 실제 구현 **주소로 채운다.** ([[언어란 무엇인가 — 분류와 컴파일·실행 모델]]에 적은 "링크는 다른 파일의 함수(`printf` 등) 위치를 찾아 연결한다"가 바로 이것.)
- 한 줄로 꿰면:
    > `#include <iostream>` = 전처리기가 **선언 묶음**을 복붙(텍스트) → 컴파일러가 그 선언으로 타입 검사 + **빈칸 남긴 기계어** 생성 → 링커가 표준 라이브러리의 **실제 구현 주소로 빈칸을 채움**.
- **"복잡해 보인다"의 정체** — 전처리(복붙)는 단순한데, 진짜 일은 그 뒤 컴파일·링크가 **선언과 구현을 따로 다루다 마지막에 합치는** 데서 벌어진다. 복잡함의 위치를 전처리로 잘못 짚었던 것.

### 확장자 없는 헤더 — 표준화·namespace의 표식
- `<iostream>`엔 `.h`가 없지만 C에선 `<stdio.h>`라고 붙여 썼다. `.h`를 뗀 건 기술적 이유가 아니라 **표준화하며 그은 선**이다(1998년 C++ 첫 국제 표준).
    1. **namespace 도입** — C++ 표준 라이브러리의 모든 이름을 `std::` 울타리 안에 넣었다(`std::cout`, `std::string`). (왜 울타리가 필요했나 = 이름 충돌 방지. namespace 자체의 깊은 얘기는 따로.)
    2. **확장자 없음 = "`std::`에 든 표준판"이라는 표식.** `<iostream>`·`<string>`·`<vector>` 모두 `.h`가 없다. 확장자 유무가 "구식(전역)이냐 / 표준(`std::`)이냐"의 시각적 구분선.
- C++은 C를 끌어안았으니 C 라이브러리도 써야 한다. 그래서 C 헤더마다 **C++용 재포장판**을 두고 규칙을 줬다 — **`c`를 앞에 붙이고 `.h`를 뗀다**(`stdio.h` → `cstdio`, `math.h` → `cmath`). 알맹이 기능은 같고, 이름이 `std::` 안으로 들어간 버전이다.

| | 정체 | 이름이 사는 곳 |
|---|---|---|
| `<stdio.h>` | C 원본 헤더 (C++에서도 호환용 허용) | 전역 (`printf`) |
| `<cstdio>` | 그 C 헤더의 C++ 재포장판 | `std::` 안 (`std::printf`) |

## 코드
```cpp
#include <iostream>   // 표준판: std::cout 등이 std:: 안에
#include <cstdio>     // C의 stdio를 std::에 담은 C++판 (std::printf)
// #include <stdio.h> // C 원본: printf가 전역에 풀림 (호환용)

int main() {
    std::cout << "hi\n";   // 컴파일: 선언으로 타입 검사 + cout 자리 빈칸
}                          // 링크: 빈칸을 표준 라이브러리의 실제 구현 주소로 채움
```

## 다른 언어에선?
- **Java — `#include`도 전처리기도 없다.** `import`는 복붙이 아니라 "이 이름을 어디서 찾을지" 알려주는 표식일 뿐이고, 컴파일러/JVM이 클래스패스에서 해당 `.class`를 찾는다. C/C++의 "텍스트 복붙 → 컴파일 → 링크"와 근본적으로 다르다 — Java는 클래스마다 독립 컴파일되고 이름공간(`package`)이 곧 디렉터리 구조다. → [[컴파일·실행 모델 비교]].
- **C와 C++** — `#include`의 복붙 동작 자체는 동일하다(C도 전처리기 복붙). 차이는 헤더 명명 규칙(`.h` vs 확장자 없음 + `c` 접두사)과 `std::` namespace의 유무.

## 막힌 것 / 의문
- **namespace(`std::`) 자체** — 이름 충돌 해결, `using` 지시문, ADL(인자 의존 탐색) 등은 C++ 고유 주제로 따로 정리. 여기선 "표준 라이브러리가 `std::` 울타리 안"까지만.
- **헤더의 그늘** — 중복 포함 방지(`#include` guard / `#pragma once`), 전방 선언(forward declaration), 헤더/소스(`.cpp`) 분리 컴파일, 그리고 헤더 복붙 모델을 대체하려는 **C++20 모듈**은 다음 패스.
- **템플릿이 헤더에 사는 이유**는 위에서 씨앗만. 분리 컴파일과 엮어 [[제네릭·템플릿 비교]]에서 본격화.
- **정적 vs 동적 링크**(표준 라이브러리가 실행 파일에 박히나, 실행 시 붙나)는 빌드·메모리 다룰 때.
- **아직 안 다룬 원본글 질문** — 1-1(벨연구소), 1-3(OOP 역사), 1-4(ANSI). 2-2(스트림 조작자)는 Questions로 분리 예정.
