# C++ `std::string` — RAII로 포장한 문자열

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 개념_ C++ ver]]의 토론에서 파생되었습니다. (2026-06-18)

## 핵심 요약
> C에는 문자열 타입이 없다 — "끝에 `\0`이 붙은 `char` 배열"을 문자열이라 *약속*했을 뿐이다. 여기서 3대 아픔이 나온다: (1) 타입 부재, (2) 길이가 데이터에 없음(`strlen` O(n) + 버퍼 오버플로), (3) 배열의 한계 상속(고정 크기, `==`가 주소 비교, 대입·이어붙이기 불가). `std::string`은 이 셋을 **RAII 두 축**으로 메운다 — 책임을 타입 작성자가 떠안고(잡고·늘리고·반납), 정리가 **스코프 끝에 결정적**으로 일어난다. Java `String`도 같은 문제를 풀지만 `delete` 없이 **GC로**(비결정적) 한다.

## 내용

### C 문자열의 정체 — 타입이 아니라 약속
- `char name[20];`은 1바이트 칸 20개짜리 배열일 뿐이다. 박히는 단위는 **바이트**(아스키 또는 UTF-8 바이트)다. 그래서 한글 한 글자는 여러 바이트(UTF-8이면 3바이트)로 쪼개져 들어가, "글자 수"와 "바이트 수"가 어긋난다. (※ "2바이트 문자 타입"은 자바 `char` 쪽 얘기 — [[문자 인코딩 비교]]에서 다룸.)
- **문자열이라는 타입 자체가 없다.** "`\0`으로 끝나는 `char` 배열"을 문자열이라 약속했을 뿐. 시작점(`name`)만 손에 쥐고, 끝은 `\0`을 만날 때까지 더듬어 찾는다.

### C 문자열의 3대 아픔
1. **타입 부재** — 문자열을 문자열로 못 다룬다. 언어가 "이건 문자열"이라고 인식하는 1급 타입이 없다.
2. **길이가 데이터에 없다** — 길이를 알려면 매번 처음부터 `\0`까지 센다(`strlen` = O(n)). 게다가 버퍼 크기(20)와 실제 내용 길이는 별개라, 내용이 넘치면 그대로 옆 메모리를 침범한다 → 버퍼 오버플로([[C 문법 조각 — 왼값·오른값과 scanf 경고]]의 scanf 사고).
3. **배열의 한계를 그대로 상속** — 크기가 고정이라 못 늘어나고(20 넘으면 끝), `name == "철수"`는 내용 비교가 아니라 **주소 비교**가 되며(둘은 다른 주소라 항상 거짓), 대입(`name = other`)·이어붙이기도 직접은 안 된다(`strcpy`/`strcat`을 불러야).

### `std::string` — RAII로 포장한 char 배열
- `std::string`은 길이를 **내부에 들고 다니고**, 내용이 길어지면 더 큰 메모리로 **알아서 옮겨 담고**(재배치), 다 쓰면 **알아서 반납**한다. 이 "잡고 / 늘리고 / 반납"이 가능한 동력이 곧 [[C++이란 무엇인가 — OOP 편한 C를 넘어서]]에서 세운 **RAII 두 축의 합작**이다.
    - **축1 — 책임의 위치(호출자 → 타입 작성자).** `string`을 만든 사람이 메모리 잡고·늘리고·반납하는 로직을 클래스 안에 한 번 박아뒀다. 쓰는 사람은 `std::string s = "철수";`만 쓰면 그 책임을 통째로 위임받는다. `malloc`/`free`/`strlen`을 손에 쥐지 않는다.
    - **축2 — 시점의 결정성(스코프 끝에 즉시).** `s`가 스코프를 벗어나는 `}` 순간, 컴파일러가 박아둔 소멸자가 호출되어 `s`가 쥔 힙 메모리를 반납한다. 네가 아무 데도 "반납해"라고 안 썼는데도, 예외로 빠져나가도, 빠짐없이.
- 3대 아픔에 정확히 대응:
    - 타입 부재 → `string`이라는 1급 타입. `==`(내용 비교), `+`(이어붙이기), `=`(대입)가 다 자연스럽게 된다.
    - 길이 부재 → 길이를 내부에 보관(`size()`가 O(1)). 넘침은 자동 확장이 흡수.
    - 배열 한계 → 동적 크기(필요하면 스스로 큰 메모리로 재배치).

### C vs C++ — "언제 정리되나"가 핵심
- **C** — `malloc`으로 잡았으면 직접 `free`를 불러야 하고, *어디서* 부를지도 책임이다. 함수 탈출 경로가 여러 개면(중간 `return`, 에러 분기) 각 경로마다 `free`를 빠짐없이 박아야 한다 — 하나라도 빠지면 메모리 누수. ([[C 제어문 — 점프로 본 분기·반복]]의 `goto` 계단식 정리가 바로 이 "탈출할 때마다 정리"를 그나마 깔끔하게 하려는 몸부림이었다.)
- **C++ `string`** — 정리 시점이 "스코프 끝"으로 **언어에 의해 못 박혀** 있다. 시점을 고를 필요도, 빠뜨릴 일도 없다.
- 그래서 `std::string`은 한마디로 **"RAII로 포장한 `char` 배열"**이다.

## 코드
```c
// C — 문자열은 char 배열 + 약속(\0)
char name[20];
strcpy(name, "철수");        // 대입도 함수로
if (strcmp(name, "철수") == 0) { /* 내용 비교도 함수로 */ }
// name == "철수"  → 주소 비교라 항상 거짓 (함정)
size_t len = strlen(name);   // 길이? 매번 \0까지 센다 (O(n))
// scanf("%s", name);        // 20 넘치면 옆 메모리 침범 (버퍼 오버플로)
```
```cpp
// C++ — std::string은 RAII 타입
{
    std::string s = "철수";   // 생성자: 힙에 메모리 잡고 복사
    s += "와 영희";           // 모자라면 더 큰 메모리로 알아서 재배치
    if (s == "철수와 영희") { /* == 가 내용 비교 */ }
    size_t len = s.size();    // 길이를 들고 다님 (O(1))
}   // ← 스코프 끝: 소멸자가 힙 메모리 반납 (예외로 빠져도 보장, free 불필요)
```

## 다른 언어에선?
- **Java `String` — `delete`가 아예 없다.** Java는 객체를 손으로 반납하는 길이 원천 차단돼 있다(`new`는 있고 `delete`/`free`는 없음). 그럼 누가 치우나 — GC.
    - `String s = new String("철수");` 뒤 스코프가 끝나도 그 객체 메모리는 **즉시 안 풀린다.** 그 객체에 닿는 참조가 다 사라지면 "수거 대상"이 될 뿐이고, **언젠가** GC가 돌 때 치워진다(비결정적). (※ `"철수"` 같은 문자열 *리터럴*은 상수 풀에 인터닝돼 따로 관리되니, GC 수거를 보려면 위처럼 `new`로 만든 객체로 본다.)

| | C++ `std::string` | Java `String` |
|---|---|---|
| 누가 반납 | 소멸자(타입 작성자가 박아둠) | GC |
| 언제 | 스코프 끝, **결정적** | 언젠가, **비결정적** |
| 네가 할 일 | 없음 (자동) | 없음 (자동) |

- **겉보기 편함("네가 할 일 없음")은 같다.** 둘 다 손으로 `free`/`delete`를 안 한다. 갈리는 건 *언제*와 *어떻게* — `string`은 소멸자가 스코프 끝에 딱, Java는 GC가 나중에 적당히. 즉 "수동 반납"(C의 `free`)이라는 같은 문제를 **C++은 소멸자로, Java는 GC로 — 정반대 방향으로 자동화**한 것이다. 메모리 누수가 C에선 흔한 버그인데 양쪽 다 거의 안 나는 이유. → 본격 비교는 [[메모리 관리 비교]].
- **char vs string 인코딩** — C `char` 배열은 바이트 단위라 한글 글자수 ≠ 바이트수. 자바 `char`는 2바이트 문자 타입이라 결이 다르다. → [[문자 인코딩 비교]].

## 막힌 것 / 의문
- **`std::string` 구현 디테일** — 짧은 문자열을 힙 없이 객체 안에 담는 SSO(small string optimization), 재배치 시 용량(capacity) 증가 전략 등은 다음 패스.
- **생짜 포인터의 `new`/`delete`, 스마트 포인터** — `string`은 RAII가 다 해주지만, 일반 자원에 RAII를 확장하는 `unique_ptr`/`shared_ptr`은 포인터·메모리 관리를 본격적으로 다룰 때. → [[메모리 관리 비교]].
- **문자열 인코딩**(바이트 vs 코드포인트, UTF-8/UTF-16) → [[문자 인코딩 비교]].
- **아직 안 다룬 원본글 질문** — 1-1(벨연구소), 1-3(OOP 역사), 1-4(ANSI), 2-1(헤더 확장자), 2-4(전처리기). 2-2(스트림 조작자)는 Questions로 분리 예정.
