# C++이란 무엇인가 — OOP 편한 C를 넘어서

> [!info] 출처
> 이 노트는 [[프로그래밍 기초 개념_ C++ ver]]의 토론에서 파생되었습니다. (2026-06-18)

## 핵심 요약
> "C++ = 객체지향 편한 C"는 절반만 맞다. 첫 이름이 "C with Classes"였던 건 사실이나, C++을 C와 가르는 무게중심은 상속·다형성(OOP)이 아니라 두 기둥이다: **RAII**(객체의 수명에 자원 정리를 묶어 언어가 책임지게 함 — 결정적 시점 + 책임이 타입 작성자에게)와 **제네릭/템플릿**(타입을 부품처럼 조립하되 성능을 내주지 않음). 상속·다형성은 그 위에 얹힌 한 갈래일 뿐이다.

## 내용

### 출발점 — "C with Classes"와 그 안의 비-OOP 씨앗
- C++의 첫 의도가 "C에 클래스를 얹어 객체지향을 편하게"였던 건 맞다. Stroustrup이 1979년 붙인 이름부터 "C with Classes"였고, 클래스·상속은 Simula에서 가져왔다.
- 그러나 첫 의도조차 OOP만은 아니었다. Simula의 클래스를 들여올 때 **생성자·소멸자**(객체가 태어날 때·사라질 때 자동으로 도는 함수)가 함께 딸려왔고, Stroustrup의 목표는 "Simula의 표현력 + C의 효율"이었다. 효율·저수준 제어가 부록이 아니라 동등한 축이었다.
- 정작 C++을 C++으로 만든 기능들은 나중에, OOP 바깥에서 왔다 — 템플릿/STL(1990년대), 이동 의미론(C++11). STL 설계자(Stepanov)는 OOP에 회의적이었고, STL은 "객체지향"이 아니라 **제네릭 프로그래밍**이다.

### 판별 기준 — "반복문 테스트"
- 강점을 가리는 기준: **대부분의 언어가 가진 것은 강점이라 부르지 않는다.** (C++의 강점으로 `for`문을 꼽지 않는 이유 — 거의 모든 언어가 반복 제어를 지원하니까.)
- 그러니 RAII와 제네릭이 진짜 C++의 강점이려면 이 테스트를 통과해야 한다. 아래에서 둘 다 통과함을 확인한다.

### 기둥 1 — RAII (자원 수명을 언어가 책임진다)
- **GC와 RAII는 같은 일이 아니다.**
    - GC가 관리하는 건 **메모리 하나뿐**이고, **사후적**이며, **비결정적**이다("언젠가 메모리 빌 때 치운다").
    - 그러나 프로그램이 잡는 자원은 메모리만이 아니다 — 파일 핸들, 락(mutex), 소켓, DB 커넥션. 공통점은 **제때 놓아야 한다**는 것이다(락을 늦게 풀면 딴 스레드가 굶고, 파일 핸들은 개수가 한정돼 고갈된다). "언젠가 풀릴 락"은 락이 아니다.
- 그래서 Java도 메모리 아닌 자원엔 GC를 못 믿고 `try-finally`(또는 `try-with-resources`)로 손으로 닫는다. 여기서 갈린다.
    - **Java** — 정리 책임이 **쓰는 사람(호출자)**에게 있다. 한 명이라도 `close()`를 까먹으면 샌다.
    - **C++ (RAII)** — 정리 책임이 **타입 만든 사람**에게 있다. 소멸자에 정리를 한 번 써두면, 그 타입을 쓰는 모두가 자동으로, **스코프를 벗어나는 순간**, **예외가 터져도** 정리된다.
- **RAII 우위 = 두 축의 결합**
    1. **책임의 위치** — 호출자 → 타입 작성자. 한 번 잘 짜두면 모두가 공짜로 안전.
    2. **시점의 결정성** — "회수하긴 한다"가 아니라 "**스코프 끝에서 즉시**". 설령 GC가 모든 걸 정리해준다 해도 *언제*는 GC 맘이라, 시점이 중요한 자원(락)엔 못 쓴다.
- 반복문 테스트 통과 — Java·C#·Python 다 "자동·결정적 소멸"이 기본이 아니다. C#은 `using`, Python은 `with`로 매번 손으로 표시한다(try-finally 계열). 기본값이 자동인 건 C++(과 이 아이디어를 빌려간 Rust)뿐. → **강점 인정.**

### 기둥 2 — 제네릭/템플릿 (타입을 부품처럼, 성능 손실 없이)
- Java는 `List<int>`가 안 되고 `List<Integer>`를 써야 한다. **`int`는 객체가 아니라 원시 타입(primitive)**이라 제네릭 자리에 직접 못 들어가고, `Integer`라는 **객체 포장지**로 감싸야 한다(박싱boxing).
- 박싱은 공짜가 아니다. `int` 100만 개를 `List<Integer>`에 담으면 — 정수마다 힙에 객체로 따로 생기고(객체 헤더 등 부가비용), 값들이 힙 여기저기 흩어져(리스트는 주소만 보관) 순회 시 CPU가 메모리를 널뛰며 읽는다(캐시 미스).
- C++ `vector<int>`는 정반대 — `int`를 포장 없이 **메모리에 연속으로** 박는다(`4바이트 × N`이 한 줄). 부가비용 없고 순회 시 한 블록을 쭉 빨아들인다(캐시 적중). 수치 연산에서 C++이 앞서는 큰 이유.
- 뿌리 — 템플릿은 `vector<int>`, `vector<double>`마다 **그 타입 전용 코드를 컴파일타임에 찍어낸다**(그래서 `int`도 직접 담는다). 반면 Java 제네릭은 컴파일 후 타입 정보를 지우고(**type erasure**) 전부 "객체"로 뭉뚱그려 한 벌의 코드로 돈다 — 그래서 객체만 받고, 박싱을 강제한다.
- 반복문 테스트 통과 — "성능을 한 푼도 안 내주는 제네릭"은 보편적이지 않다(Java는 박싱 비용을 낸다). → **강점 인정.**

### 결론 — 입장의 정밀화
- 처음 입장: "C++ = OOP 편한 C."
- 고친 입장: **"C++의 무게중심은 OOP가 아니라, 객체의 수명(생성~소멸)을 언어가 책임지게 한 RAII + 타입을 부품처럼 조립하는 제네릭이다."** 상속·다형성은 그 위에 얹힌 한 갈래.
- 이것이 원본글 질문1-2("학부는 왜 C++을 객체지향의 핵심처럼 가르치나")의 답이다. 절반은 교육적 편의(절차지향 → 객체지향의 다리). 그 탓에 RAII·템플릿이라는 두 기둥이 가려진다. "객체지향 활용이 별로 없더라"는 체감은 착각이 아니라 **C++의 진짜 알맹이를 본 것** — 이름만 잘못 붙였을 뿐이다.

## 코드
```cpp
// RAII — 소멸자가 스코프 끝에서 자동·결정적으로 정리
{
    std::ifstream f("data.txt");  // 생성자가 파일 열기
    // ... 사용 ...
}   // 스코프 종료: 소멸자가 파일 닫음 (예외로 빠져나가도 보장)

// vector<int> — 포장 없이 연속 저장
std::vector<int> v = {1, 2, 3};   // [4B][4B][4B] 메모리에 한 줄로
```
```java
// Java — 메모리 외 자원은 손으로 (책임이 호출자에게)
try (var f = new FileInputStream("data.txt")) {   // try-with-resources
    // ... 사용 ...
}   // close() 호출됨 — 단, try 블록으로 직접 감싸야 함

List<Integer> list = List.of(1, 2, 3);   // int를 Integer로 박싱(힙에 산재)
```

## 다른 언어에선?
- **RAII** — Java는 GC(메모리, 비결정적) + `try-finally`/`try-with-resources`(그 외 자원, 수동). Rust는 C++의 RAII를 통째로 빌려가 소유권 모델의 토대로 삼았다. C는 자동 장치가 없어 `goto` 계단식 정리로 흉내 낸다([[C 제어문 — 점프로 본 분기·반복]]). → 본격 비교는 [[메모리 관리 비교]].
- **제네릭** — C++ 템플릿(컴파일타임에 타입별 코드 생성) vs Java 제네릭(type erasure, 런타임엔 객체로 뭉갬). → [[제네릭·템플릿 비교]].
- 관통 대비 재확인 — [[C 자료형 — 정수와 실수의 표현]]부터 반복된 "C는 자유·하드웨어 밀착, Java는 안전·통일"의 또 다른 결. C++은 그 사이에서 **안전(RAII)과 성능(템플릿)을 동시에** 노린다.

## 막힌 것 / 의문
- **type erasure 내부, GC 내부 동작**은 [[지침]]의 외부 학습 경계(JVM)와 겹친다. 여기선 "Java는 지우고/비결정적, C++은 박아넣고/결정적"까지만. 깊이는 JVM 정리와 "거긴 어떻게 정리했어?"로 연결.
- **OOP 역사**(원본글 질문1-3, Simula·Smalltalk·PARC)도 외부 학습 영역. C++이 Simula에서 클래스·소멸자를 가져왔다는 연결고리만 남기고 보류.
